0. Executive Summary / 执行摘要
《旅游模拟器 / Travel Simulator》V1 的本质不是赛车游戏、开放世界真实驾驶或现实地图导航系统，而是一套以长
途公路旅行感为核心的后端权威旅行模拟系统。玩家选择路线与车辆后，在像素风道路中在线驾驶或离线推进，沿途
经历路线段、天气、昼夜、景点停靠、照片卡、车辆维护、路线完成和新路线解锁。
V1 选择 Curated Route Packs / 手工配置路线包，是因为第一版需要控制路线长度、节奏、景点密度、奖励、背景和
维护压力。真实全球地图、Google Maps、真实导航、复杂交通 AI、真实天气 API 与大型物理驾驶模拟都会显著扩大
工程边界，却不能更快验证核心循环。
Trip Simulation Engine / 旅程模拟引擎是 V1 的技术核心，负责距离、速度、油耗、清洁度、耐久度、强制停靠、路
线终点、离线推进和奖励计算。Economy Ledger / 经济流水系统负责所有货币变动的原子化、幂等和可审计。
Route Config System / 路线配置系统负责路线包、路段、景点、天气、昼夜、奖励倍率、配置版本和回滚。
后端必须权威。客户端只能提交 Hold to Drive / 长按驾驶、Auto Driving / 自动驾驶、Hold to Boost / 长按加速、领
取、拍照、开始路线等玩家意图；距离、奖励、离线时间、抽卡结果、钱包变化都不能由客户端决定。所有关键行为
必须由后端埋点，所有数值必须通过 Admin Config 配置。
V1 成功标准是：玩家能顺畅完成第一趟教程，愿意回来领取 Travel Report / 离线旅行报告，愿意维护车辆继续下一
段旅程，愿意收集下一张照片卡，并且不会把 Gacha 理解成付费进度墙，也不会把燃油系统理解成体力系统。
核心结论

落地要求

V1 是旅行模拟，不是赛车或真实导航

保持路线包、景点、照片、车辆维护和离线回归的核心体验。

Trip Simulation Engine 优先级最高

先实现后端权威 tick、离线模拟、forced stop、奖励和车辆消
耗。

Economy Ledger 必须严谨

所有 Road Coins、Travel Tokens、Souvenir Stamps、
Stamp Fragments、Blueprints 变化都写
wallet_transactions。

Route Config System 必须配置化

路线、数值、天气、任务、Gacha、维护价格、奖励倍率均通
过后台版本发布。

离线系统服务留存，不替代在线

max_offline_hours=8；离线 Road Coins 为 4/km，低于在线
10/km。

Gacha 只做收藏和外观

Gacha 不影响玩家能否继续旅行，不参与路线解锁。

3. V1 Client Gameplay Presentation / 主界面表现与玩家体验层
3.1 主屏幕驾驶表现
主屏幕应让玩家持续感到“车正在路上”。玩家车辆以像素风视觉在道路上前进，路边环境根据 route segment 切
换。客户端可以根据后端返回的 current_distance_km、segment、weather、day_phase 做动画插值，但最终状
态以后端返回为准。
《旅游模拟器 / Travel Simulator》V1 Clean Final Technical Report | 第 11 页

3.2 像素风 route segment 背景切换
路线段决定背景：城市、海岸、沙漠、森林、雪山、平原、夜景、高速公路、山路等。每个 segment 绑定
background_pack_id、terrain_type、biome、speed/fuel/cleanliness/durability multiplier。客户端无需知道真
实经纬度，只需根据后端当前 segment 播放对应背景。

3.3 天气/昼夜表现
天气和昼夜影响画面色调、粒子、UI 氛围和照片卡。Sunny 更明亮，Rain 增加雨线和反光，Fog 降低远景可见度，
Snow 增加冷色和雪粒，Sandstorm 叠加黄沙色调。Dawn、Day、Sunset、Night 影响天空、路灯、照片氛围和部
分任务。

3.4 Route Board
Route Board 是主界面信息中枢，应显示：下一个城市、下一个景点、剩余距离、当前天气、昼夜阶段、当前路线进
度、车辆油量/清洁度/耐久度、是否处于 Forced Stop。显示值来自 GET /player/state 或 GET /trip/current，不由
客户端自行结算。

3.5 Travel Report UI
Travel Report 应以视觉化方式展示昨夜行驶距离、奖励、油耗、车辆损耗、天气变化、是否到达景点、是否因为
LOW_FUEL / LANDMARK_REQUIRED / ROUTE_END 停靠。报告中的奖励为 pending，玩家点击 claim 后，后端写
入 wallet_transactions 并返回结果。

3.6 景点停靠与照片卡
到达景点时车辆自动停靠，屏幕展示 avatar + car + scenery 的照片卡构图。玩家拍照后获得 Photo Card，照片质量
由清洁度、天气、昼夜、景点稀有度共同影响。强制景点未处理前不允许继续越过该点。

3.7 客户端预测动画与后端权威状态
客户端可以做短时预测动画，以减少操作延迟，但预测只用于表现。每次 drive tick 后必须用后端返回的
current_distance_km、vehicle_state、rewards、forced_stop_reason 纠正。若预测与后端差距过大，客户端应
平滑回拉，而不是继续相信本地状态。

begin transaction
if exists idempotency_key:
return previous_result
trip = SELECT * FROM player_trips WHERE trip_id = ? FOR UPDATE
assert trip.player_id == player_id and trip.status == 'ACTIVE'
vehicle = SELECT * FROM player_vehicles WHERE id = trip.player_vehicle_id FOR UPDATE

apply fuel / cleanliness / durability losses
update trip distance and last_simulated_at
rewards = grant_trip_rewards(player_id, trip, final_distance, mode='ONLINE')
emit analytics and risk logs
commit

begin transaction
player = SELECT * FROM players WHERE player_id = ? FOR UPDATE
trip = SELECT active trip FOR UPDATE
if trip is null: update player.last_seen_at; commit; return no_report
if exists unclaimed offline_report for trip:
return existing_pending_report

clamp by fuel_limited_distance, required landmark, route end

commit

Travel Report 是离线系统的回归奖励界面和审计载体。报告中的奖励先 pending，玩家点击领取后才写入钱包流

21.2 数据库事务边界与一致性要求


钱包扣费和发奖必须与业务状态更新在同一个数据库事务内完成。



player_trips 在线 tick、离线模拟、路线完成必须使用 SELECT … FOR UPDATE 锁定当前 trip。



player_vehicles 维护状态更新必须和对应扣费流水同事务。



gacha_pity_state 必须在抽卡事务中锁定；抽卡历史与钱包扣费同事务。



配置表发布后不可原地修改；新版本通过 config_versions 发布，旧版本标记为 DEPRECATED。

23. Trip Simulation Engine
Trip Simulation Engine 是 V1 最重要的技术地基。它不是前端动画系统，而是后端权威的旅程状态推进器。所有行
驶距离、油耗、耐久、清洁度、景点停靠、路线完成、在线/离线奖励，都应由该引擎计算并写入数据库。

function calculate_distance_gain(vehicle, segment, weather, mode, duration_seconds):
mode_multiplier = get_mode_multiplier(mode)
condition_multiplier = get_durability_speed_multiplier(vehicle.current_durability) * weather.speed *
fuel_state_multiplier(vehicle.current_fuel)
return max(vehicle.base_speed_kmph * duration_seconds / 3600 * mode_multiplier * condition_multiplier *
segment.speed_multiplier, 0)
function calculate_fuel_used(distance_km, vehicle, segment, weather, mode):
return max(distance_km * vehicle.fuel_consumption_per_km * weather.fuel * segment.fuel_multiplier *
get_durability_fuel_penalty(vehicle.current_durability) * get_mode_fuel_multiplier(mode), 0)
function calculate_cleanliness_loss(distance_km, vehicle, segment, weather):
return clamp(distance_km * vehicle.cleanliness_loss_per_km * weather.cleanliness *
segment.cleanliness_multiplier, 0, vehicle.current_cleanliness)
function calculate_durability_loss(distance_km, vehicle, segment, weather):
adjusted_weather = 1 + (weather.durability - 1) * (1 - vehicle.weather_resistance)
return clamp(distance_km * vehicle.durability_loss_per_km * segment.durability_multiplier * adjusted_weather,
0, vehicle.current_durability)
function check_for_forced_stop(trip, vehicle, route, landmarks, effective_fuel_per_km):
if vehicle.current_fuel <= 0: return ForcedStop('LOW_FUEL', 0)
route_remaining = route.total_distance_km - trip.current_distance_km
distance_to_landmark = distance_to_next_required_landmark(landmarks, trip.current_distance_km)
fuel_limited_distance = vehicle.current_fuel / effective_fuel_per_km
distance_limit = min(route_remaining, distance_to_landmark, fuel_limited_distance)
if distance_limit == fuel_limited_distance: return ForcedStop('LOW_FUEL', distance_limit)
if distance_limit == distance_to_landmark: return ForcedStop('LANDMARK_REQUIRED', distance_limit)
if distance_limit == route_remaining: return ForcedStop('ROUTE_END', distance_limit)
return ForcedStop(null, distance_limit)

':coins')
accumulate online_token_meter, grant 1 token per 10 km
if kind == 'OFFLINE':

V1 玩家规模、团队规模和系统复杂度尚未证明需要拆分；钱包、旅程、车辆、任务之间事务耦合高，过早拆服务会
增加分布式事务复杂度。

28.2 为什么不一开始 Kubernetes
Kubernetes 适合规模化编排，但早期会增加部署、监控、安全、成本和运维难度。V1 应先用托管方案快速验证核心
循环。

34. 最终架构师建议
V1 最重要不是内容多，而是核心循环稳定。对于《旅游模拟器 / Travel Simulator》，第一版的胜负不在于是否有真
实地图、真实导航或复杂多人，而在于玩家是否愿意完成第一趟、回来领取 Travel Report、维护车辆、继续下一段
旅程、收集下一张照片卡。
1.

先做 Trip Simulation Engine。 在线行驶、离线推进、油耗、景点停靠、奖励和路线完成都依赖它。引擎不稳，增加车
辆、路线、Gacha 都没有意义。

2.

钱包系统必须严谨。 Road Coins、Travel Tokens、Souvenir Stamps、Stamp Fragments、Blueprints 都必须有余
额、有流水、有 reason、有 source、有幂等。

3.

路线系统必须配置化。 Curated Route Packs 才能控制路线长度、景点节奏、天气、背景、奖励和难度。

4.

离线系统要克制。 离线用于留存和旅行感，不是替代在线；离线收益必须低于在线，离线报告必须 pending 领取。

5.

Gacha 只做收藏和外观。 Gacha 不决定路线能否继续，不能成为路线解锁 paywall。
《旅游模拟器 / Travel Simulator》V1 Clean Final Technical Report | 第 70 页

6.

第一趟教程必须短、顺、有正反馈。 80-120 km、免费、快速引导 Hold to Drive、Auto Driving、第一个景点和第一次
拍照。

7.

不要一开始做真实地图。 真实地图和真实导航会放大复杂度，却不能更快验证核心循环。

8.

所有数值必须后台配置。 路线距离、油耗、维护价格、离线时长、任务奖励、Gacha 概率、天气权重和解锁成本都必须
可调。

9.

每个关键行为必须埋点。 没有 Analytics，就无法判断教程、路线、维护、离线和经济是否健康。

10.

V1 成功标准很明确。 玩家愿意回来领取离线报告，愿意继续下一段旅程，愿意维护车辆，愿意解锁下一条路线，愿意收
集下一张照片卡。
